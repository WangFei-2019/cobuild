# 共建 · CoBuild

一个围绕「目标、分工、进展、交付与验收」的小团队项目协作应用。使用 React 19 与 Ant Design 6，提供独立项目空间、成员跨项目视图和可核对的计划调整流程。

本仓库以 **Node.js 正式协作服务**为实际使用方式：真实账号、邀请、权限与服务器持久化。GitHub Pages 提供工作区连接入口；本地演示独立保留在 `demo.html`。

[正式工作区](https://123.57.227.212:5175/) · [GitHub 入口](https://wangfei-2019.github.io/cobuild/) · [独立演示](https://wangfei-2019.github.io/cobuild/demo.html#/dashboard) · [产品与设计依据](设计依据.md)

| --- | --- | --- |
| 项目、成员、任务、里程碑、成果交接 | 当前浏览器内操作并保存 | 服务端保存，按账号权限共享 |
| 工作台与搜索 | 示例人员的跨项目工作 | 当前真实账号的可见工作 |
| 登录与邀请 | 明确标注的本地体验，无真实邀请 | 自助注册、真实账号、项目邀请、访问控制 |
| 项目体检与简报 | 根据当前记录运行可解释规则，简报可编辑、复制和下载 | 同样支持，分析范围遵循当前项目访问权限 |

## 产品能力

- **我的工作台**：个人待办按项目分组，切换我推进、待我验收、需协助与全部相关待办；每条任务带实际项目色边与项目名标签，列表、表格和手机一致；项目范围、期限筛选和任务数量一致，跨项目搜索独立呈现可访问结果。
- **独立项目空间**：项目说明、目标、任务列表与看板、成员、里程碑、成果、动态和设置各自有明确入口。
- **自选项目颜色**：创建与项目设置都支持预设、调色板和 HEX 色值，项目导航与来源标记同步更新。
- **人员与项目成员分开管理**：人员目录添加与编辑姓名、简介、颜色；职责与访问角色按项目设置。完整服务可生成邀请链接，由已有账号或新注册人员确认加入；Pages 只管理本地档案，不生成真实邀请。
- **统一成员档案**：按项目颜色查看一个人参与的项目、分工、进度与成果，区分本人提交和旧记录按任务归属。
- **交付闭环**：明确负责人、接收人、前置任务和验收要求，提交成果、退回修改、重新交付及确认；阶段验收依据实际任务交接。
- **可检查的规划**：载入明确标注的示例草案，修改里程碑、分工、日期与依赖；调整剩余工作时先看前后对比，再确认，保留已有成果和验收记录。
- **报告导出**：导出项目、里程碑及验收记录、任务日期和依赖、受阻项、成果版本与最近动态。
- **项目副驾**：查看每一条风险的记录依据和建议动作，分开呈现完整交接、完成标记、期限和依赖；编辑一份五段式简报草稿，再复制或下载。
- **外部 AI 方案往返**：在副驾填写要求，预览并复制规划提示词，在自己选择的 AI 中生成结构化方案，再导入共建。项目、原始版本、模式、成员、日期、依赖和受保护成果均要校验，确认前不会更新项目。

所有演示人物与项目均为合成示例。修改只影响当前浏览器；清除站点数据或重置演示会移除本地改动。演示版不包含 API Key，不代发邀请，不提供真实账号认证或跨设备同步，也不会把预置规划称为真实 AI 输出。

副驾的体检与简报是本地规则整理，不能证明成果质量，也不预测工时或完成日期。外部 AI 流程由用户主动复制资料，应用不会替用户发送；请先核对提示词预览。导入格式为 `cobuild-plan-exchange-v1` 信封，包含 `projectId`、`baseRevision`、`mode` 和 `draft`；返回方案必须保留这些元信息。项目在 AI 处理期间变化时，需要重新导出最新上下文。简报文字的编辑暂存于当前页面，离开前请复制或下载。

## 本地运行 Pages 演示

需要 Node.js 24 或更新版本，使用 package.json 指定的 pnpm 版本：

```sh
pnpm install --frozen-lockfile
pnpm build:pages
pnpm preview:pages
```

打开终端显示的 `http://127.0.0.1:4173/cobuild/` 进入工作区连接页；本地演示在 `http://127.0.0.1:4173/cobuild/demo.html#/dashboard`。演示沿用原浏览器存储，不自动重置；哈希路由支持任务链接、前进/后退和刷新。端口被占用时可运行 `node scripts/preview-pages.mjs --port 4174`。

`dist-pages/` 是独立静态产物，不要把正式服务端的 public/ 直接作为 Pages 网站发布。静态构建会检查演示适配已经包含，并拒绝混入 server、SQLite 账号和项目存储模块。

## 发布到 GitHub Pages

源码应作为一个独立仓库的根目录，package.json 与 .github/ 在同一级，不要将包含其它项目的父目录一起上传。

1. 将干净源码推送到仓库 main 分支。
2. 在仓库 Settings → Pages 中选择 **GitHub Actions**。
3. Pages 工作流执行测试、安装锁定依赖、静态构建并部署。成功后以工作流输出的页面地址为准。

默认仓库名为 cobuild 时，页面形如 `https://OWNER.github.io/cobuild/`。正式协作仍需部署后端。可在仓库 Actions Variables 中设置公开变量 `COBUILD_SERVICE_URL=https://你的服务地址:端口`，覆盖本仓库工作流已预置的当前线上地址；本地构建未配置时由用户填写。只允许 HTTPS 根地址，入口仅导航，不代理密码、会话或项目数据。模型密钥绝不放入此变量。完整步骤、发布包校验及可选服务器部署见 [GitHub 发布与部署](GitHub发布与部署.md)。

## 运行完整服务端版本

```sh
pnpm build
pnpm start
```

访问 `http://127.0.0.1:4173`，首次使用由本人设置工作区管理员。新安装从零项目、零示例人员开始，设置后只有真实管理员，可直接创建首项目并邀请伙伴。已有项目与旧成员历史保留，管理员是独立的新成员；历史人员通过邀请认领，不按同名自动合并，也不能通过身份切换冒充接收人。

管理员完成首次设置后，其他使用者可在 `/register` 自行创建普通账号。注册后进入自己的空工作区，可创建项目并成为该项目管理员，也可通过邀请加入他人的项目。已绑定账号的伙伴必须接受邀请后获得项目访问；单纯添加档案不会授权账号。普通账号只能访问自己参与的项目；工作区管理员仍可管理与查看工作区中的项目。

项目管理员、成员和只读权限在服务端执行。成果由指定接收人确认；修改交付约定后需要重新交付和确认。AI 调用由服务端配置，外部接口使用 HTTPS，密钥不返回浏览器。生成草案与查看差异不会写入项目，确认应用检查版本，冲突时保留当前数据。

公开服务需 HTTPS、持久化存储与单写入实例。已提供自包含 Dockerfile、Compose/Caddy 与可选 GHCR 工作流。具体配置、完整备份方式和模型接入见 [部署与配置](部署与配置.md)。账号邮件验证、密码找回和邮件通知尚未交付；邀请目前由用户复制链接分享。

## 工程检查

```sh
pnpm test
pnpm build
pnpm build:pages
pnpm doctor
# 在提供公开地址与初始化口令的服务端环境中：
node scripts/doctor.mjs --production
```

模型协议测试只使用本机 fixture，不需要真实密钥。doctor 只读检查运行时、构建资源、存储写入权限和服务配置，不初始化数据库，不联网调用模型，也不保证真实模型余额和能力。

发布脚本按白名单生成可校验的独立发布包，不包含 .local、数据库、上传文件、.env、.secrets、截图或父目录其它应用。安全边界见 [SECURITY.md](SECURITY.md)，本轮变化见 [CHANGELOG.md](CHANGELOG.md)。
